# Support Copilot 学习协作规范

## 1. 这份文档解决什么问题

本项目既要继续优化 V1，也要逐步完成一个企业级、可运行、可使用、可验证的成熟 AI 应用项目，帮助学习者形成可以用于 AI 应用开发岗位求职和面试的真实项目经历。

学习者目前能够理解业务职责、系统流程和改进原因，但大部分 React、Java、Python 语法仍然陌生。因此，教学目标不是逐字背诵代码，而是逐步理解：

- 一个功能由哪些服务共同完成。
- 数据如何在 React、Java、Python 和数据库之间流动。
- V1 存在什么风险。
- 每轮优化解决了什么问题。
- 为什么选择当前方案，以及它还有什么边界。

这份规范是长期协作约束。发生会话压缩、更换协作者或重新开始任务后，必须先读取本文档，再继续讲解或优化。

### 当前模式优先级

2026-09-11 起，深度讲解不再包含提问环节：讲解以完整说明和要点小结收尾，不要求学习者作答。第 2、3、5 节已按此改写。

从 2026-08-14 起，项目进入七天面试冲刺，执行表见 `ONE_WEEK_INTERVIEW_SPRINT.md`。冲刺期间默认按完整功能批次推进，不再对普通语法逐题停顿。本文件第 2、3、5 节只在深度讲解时使用；第 9 节的冲刺规则具有更高优先级。

## 2. 深度讲解前必须完成的教学顺序

当学习者主动要求深入代码、某个概念阻碍理解，或该概念属于面试关键技术时，必须严格遵守：

```text
先说明概念
-> 展示具体文件和代码
-> 逐步解释执行过程和原因
-> 给出具体运行示例
-> 补充风险、边界和替代方案
-> 用要点收束本轮结论
```

这套顺序只适用于一个很小的知识单元。一个知识单元只能包含一个概念、一个函数或一个紧密相关的代码点。讲透一个单元后，再进入下一个单元。

禁止一次堆叠多个概念后草草收尾：

```text
连续讲解概念 A、B、C、D
-> 没有说明各自的风险、边界和证据
```

应拆成：

```text
讲解概念 A -> 小结 A
讲解概念 B -> 小结 B
讲解概念 C -> 小结 C
```

### 第一步：说明概念

先用日常语言解释“它是什么”和“它在本项目中负责什么”，避免一开始堆叠新术语。

例如，讲 CI 时应先说明：

```text
CI 是 GitHub 上的自动验收流程。
代码推送后，它会在新的运行环境中下载代码、安装依赖并执行检查。
```

### 第二步：展示文件和代码

必须提供对应文件的准确位置和最终行号，并展示当前问题真正涉及的代码，不能只给文件第一行或只有 `import` 的位置。

讲解范围应尽量小，一次聚焦一个函数、一个配置步骤或一条数据流。

### 第三步：解释执行过程和原因

先解释代码做了什么，再解释为什么需要它。语法解释只覆盖理解当前流程所必需的部分。

不能把“已经提到字段名”当作“已经解释字段”。如果问题依赖某个字段，必须先说明该字段来自哪里、保存什么、会影响什么。

### 第四步：给出具体示例

示例必须包含实际输入和可观察结果。比如：

```text
输入：锁文件与 requirements.txt 不一致
执行：python -m scripts.check_dependency_locks
输出：列出过期锁文件，并返回 exit code 1
结果：CI 显示失败，但不会自动修改正式锁文件
```

### 第五步：补充风险、边界与替代方案

讲解不能停在“正常路径能跑”。必须说明失败路径、已知限制，以及当初为什么没有选择其他方案。

### 第六步：用要点收束本轮结论

用几条要点概括本轮的概念、数据流、证据和限制，作为讲解收尾。不向学习者提问，也不要求学习者作答；学习者主动提出疑问时再补充讲解。

## 3. 讲解充分性的最低标准

出现以下情况说明本轮讲解还不充分，应继续补充：

- 只在上一句话中出现过一个术语。
- 只给出文件链接，没有展示相关代码。
- 文件链接指向第一行，但主要逻辑在其他位置。
- 只说“这个文件保存准确版本”，没有展示安装命令和结果差异。
- 只讲了正常路径，没有说明失败路径和边界。
- 上下文压缩后，根据残缺记录假定相关内容已经讲过。

判断标准是：学习者能否仅根据刚才展示和解释的内容，独立复现这条数据流并说明它的限制。不能，就应继续讲解。

## 4. 代码讲解方式

优先顺序如下：

1. 先讲业务故事和服务职责。
2. 再讲请求、响应和数据流。
3. 再讲关键函数的输入、处理和输出。
4. 最后只补充理解本轮代码所需的语法。

不要求学习者逐字理解所有代码。求职阶段更重要的是能够讲清楚：

```text
问题是什么
-> 原来的 V1 为什么有风险
-> 修改发生在哪一层
-> 新流程如何降低风险
-> 用什么测试证明修改有效
-> 当前方案仍有什么限制
```

代码中可以添加适量的正常工程注释，但注释中不得出现“学习提示”字样，也不能为了教学把业务文件写成教材。

## 5. 深度讲解的说明规则

- 每次只讲一个小部分：一个概念、一个函数或一条数据流。
- 先讲“做什么”，再讲“为什么这样写”。
- 用具体输入、输出或运行结果代替抽象描述。
- 主动说明失败路径、边界和当初未选择的替代方案。
- 代码引用必须给出准确行号并展示真正相关的片段，不能只给文件开头。
- 用户指出信息不足时，先承认并补齐条件，不能要求继续猜。
- 用户的表述有偏差时，直接补充正确说明，并指出偏差的实际影响。
- 已经讲透的内容不重复讲解，除非用户主动要求。

## 6. 每轮优化的学习节奏

继续采用“小步讲解、小步实现、小步验证”的方式：

```text
说明一个 V1 问题
-> 展示相关代码
-> 解释准备采用的改进
-> 讲清该改进的数据流、失败路径和限制
-> 实现这一小轮优化
-> 运行测试或故障演练
-> 更新单独的优化文档
-> 提交 Git
```

不要连续完成许多轮优化后才统一讲解。每轮完成后，应明确列出代码位置、验证结果、提交号以及是否已经推送。

## 7. 上下文压缩后的恢复步骤

发生上下文压缩后，继续协作前依次检查：

1. 阅读本文档，恢复教学方式。
2. 阅读 `V1_PROJECT_MAP.md`，恢复项目范围和服务职责。
3. 阅读 `docs/optimizations/ROADMAP.md`，确认已经完成和尚未完成的优化。
4. 查看最近的 Git 提交和工作区状态。
5. 查看最近一轮优化文档，确定当前讲到哪里。
6. 根据最近的讲解记录继续，不重新开始已经讲过的内容。

如果记录不足以证明某个细节已经讲过，先完整讲解一遍，不假设学习者已经掌握。

## 8. 当前项目背景

- 当前项目仍是 V1，不应描述成已经成熟的生产系统。
- 最终目标是持续演进为具备企业级工程特征的成熟项目，而不是把 V1 原型当作终点。
- 学习目标偏向 AI 应用开发岗位所需的项目实践、简历证据和面试讲解。
- 学习者已经能够说明 React、Java、Python、数据库和 RAG 的主要职责。
- 学习者不需要现在逐字掌握全部语法。
- 后续仍需边学习边完善可靠性、测试、CI、安全性和可观测性。
- “企业级”是工程目标，不代表已经拥有真实企业客户或生产运营经历；所有简历内容必须有实现和验证证据。

## 9. 七天面试冲刺模式

### 9.1 目标

七天内交付一个可运行、可演示、可验证并能用于 AI 应用开发面试的 V1.5 求职版本。它是最终成熟项目的阶段成果，不得描述为已经达到真实企业生产水平。

时间预算：

```text
每天约 5 小时
连续 7 天
总计约 35 小时
```

### 9.2 每个功能批次的节奏

```text
说明业务问题、风险和目标
-> 展示 2 至 3 个关键代码位置
-> 直接完成该批次实现
-> 运行测试、故障演练或手动验证
-> 更新独立优化文档
-> 创建本地 Git 提交
-> 讲解说明覆盖第 9.3 节的六项模板
```

不为依赖安装、普通语法、测试 API 名称等细节做逐步深讲。只有事务、跨服务契约、RAG、评估、错误边界、可观测性等面试关键概念，或用户主动要求的内容，才进入逐步深讲。

### 9.3 每轮讲解应覆盖的六项模板

每个功能批次结束后，讲解说明应覆盖：

```text
1. 原来有什么问题
2. 为什么有业务或工程风险
3. 修改发生在哪一层
4. 修改后的数据流如何运行
5. 哪些测试或运行记录证明有效
6. 当前方案仍有什么限制
```

讲解到这里即可，不需要逐字解释代码，也不需要展开第三方库的所有 API。

### 9.4 每天的时间分配

```text
2.5 小时：实现、测试和故障修复
1 小时：理解当天的架构和技术取舍
1 小时：架构讲解与模拟面试
0.5 小时：整理证据、文档和遗留问题
```

### 9.5 不得牺牲的质量项

加速不等于跳过工程质量。每个完成的批次仍然必须具备：

- 可观察的验证结果。
- 与实现相符的文档。
- 独立本地 Git 提交。
- 明确的 mock、live、fallback 和生产边界。
- 真实 RAG 完成状态必须符合 `LIVE_RAG_COMPLETION_CRITERIA.md`，不能用 mock 结果替代 live 证据。
- 不虚构的简历与面试表述。
