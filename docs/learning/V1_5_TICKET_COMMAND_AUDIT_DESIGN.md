# V1.5 工单命令与审计设计

> 学习状态：设计讲解已完成，尚未修改业务代码。

## 1. 当前更新接口的问题

当前 `UpdateTicketRequest` 使用普通可空字符串，`TicketService.update()` 通过 `null` 判断是否更新字段。

这会把下面两种请求都转换成 Java `null`：

```json
{}
```

```json
{
  "assigneeName": null
}
```

系统因此无法区分：

- 字段未出现，保持原负责人。
- 字段明确为 `null`，取消负责人。

## 2. PATCH 的三种状态

通用 PATCH 字段需要表达：

```text
present = false
→ 字段未出现，不修改

present = true, value = null
→ 明确清空

present = true, value = "李四"
→ 设置新值
```

普通 `String` 不能保存“字段是否出现”，需要带 `present` 标记的包装类型，或者使用支持三态语义的 JSON Patch 方案。

## 3. 重要动作使用明确命令

当“领取工单”或“取消负责人”涉及权限、状态规则、原因和审计时，可以使用明确的业务接口，而不是只暴露通用字段修改。

示例：

```http
POST /api/tickets/{id}/unassign
```

请求体提交操作原因，操作人身份不由客户端自由填写。

## 4. 操作人身份

可信审计信息应来自不同来源：

```text
操作人
→ Java 已验证的登录身份或 SecurityContext

操作原因
→ 请求体，并由 Java 校验

操作时间
→ Java 服务器时间
```

不能完全相信请求体中的 `operatorName`，否则客户端可以伪造管理员身份。当前 V1 使用 `permitAll()`，因此在真实审计前还需要身份认证和权限校验。

## 5. TicketEventResponse 不是审计实体

当前 `TicketEventResponse` 只是返回给 React 的 DTO。`TicketService.toResponse()` 每次临时拼出“工单创建”和最新一次“辅助分析完成”，并没有持久化负责人变更历史。

真正的审计需要独立的 `TicketEvent` 实体和 Repository。事件至少应考虑：

- 事件 ID。
- 工单 ID。
- 事件类型。
- 操作人 ID。
- 操作原因。
- 操作前后的必要状态。
- 服务器生成的时间。

## 6. 工单更新和审计必须原子保存

负责人变更和审计事件属于同一个业务动作，应位于同一个事务中：

```text
检查权限和状态
        ↓
修改 Ticket
        ↓
追加 TicketEvent
        ↓
两项都成功：commit
任何一项失败：rollback
```

不能允许“负责人已经改变，但没有审计记录”的半完成状态。

## 7. 审计事件只追加

审计事件通常不直接覆盖或删除。发现原因错误时，应保留原事件并追加更正事件。

```text
原事件：取消分配，原因 A
更正事件：正确原因是 B
```

这样才能保留真实操作过程，并降低修改历史记录造成的审计风险。

## 8. 本次设计边界

本次只确定：

- PATCH 三态问题。
- 重要操作使用业务命令的理由。
- 操作人必须来自可信登录身份。
- 审计事件需要持久化。
- 工单更新和事件追加必须处于同一事务。
- 审计事件采用只追加方式。

具体认证方案、权限模型、审计数据加密和保留期限属于后续独立设计。
