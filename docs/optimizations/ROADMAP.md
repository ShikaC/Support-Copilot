# Support-Copilot 后续优化路线

> 文档状态：执行路线
> 基线日期：2026-08-11
> 适用范围：当前仓库的 V1 本地端到端原型，及其迈向成熟项目的持续优化
> 目标：把项目完善为企业级、可运行、可使用、可验证，并能服务于 AI 应用开发岗位求职的成熟 AI 应用作品
> 重要边界：本文档是路线，不代表其中所有能力已经实现或已经由作者本人验证。

---

## 1. 路线结论

Support-Copilot 后续不应继续以“增加页面数量”作为主要目标。最合理的路线是：

1. 先冻结当前工作区的可复现基线。
2. 再建立固定评估集，证明 mock 分析链路确实符合预期。
3. 然后修正 Java、Python、React 三层之间的契约和失败语义。
4. 在有可用 API、预算和网络条件时，再单独验证 live 模式。
5. 最后补充安全边界、可观测性、演示材料和发布说明。

项目的完成目标是具备企业级工程特征的成熟作品，而不是停留在演示原型。由于项目尚无真实企业生产运营经历，“企业级”必须由完整实现和验证证据支撑，不能被表述为已经服务真实企业客户。最终需要清楚证明以下能力：

- 能把业务流程拆分为 Java 业务服务和 Python AI 服务。
- 能用结构化数据承载分类、检索、证据、回复和人工升级结果。
- 能区分 mock、live 和 fallback，避免把模拟结果伪装成真实模型结果。
- 能处理知识不足、模型不可用、版本冲突和接口错误。
- 能用固定数据集评估分类、检索、引用和降级行为。
- 能解释系统当前的能力边界，而不是只展示一个漂亮页面。

## 2. 当前基线

### 2.1 当前架构

~~~text
React + TypeScript + Ant Design + ECharts
                  |
                  | /api
                  v
     Java 21 + Spring Boot + JPA + H2
                  |
                  | /analyze
                  v
    Python 3.11 + FastAPI + LangChain
                  |
                  | live 模式可选
                  v
        OpenAI Responses / Embeddings
~~~

当前服务职责：

| 服务 | 当前职责 | 不应承担的职责 |
| --- | --- | --- |
| React Web | 工作台、工单列表、分析结果、证据、建议回复、状态展示 | 直接决定业务事实、直接调用模型、伪造成功结果 |
| Java API | 工单业务状态、分析历史、持久化、版本检查、业务 fallback | 编写复杂 Prompt、替代 Python 检索逻辑 |
| Python AI | 工单结构化分析、分类、检索、回复草稿、live/mock/fallback | 修改 Java 业务数据、绕过人工审核 |
| H2 | 当前本地演示数据和分析历史 | 生产持久化 |
| 本地知识文件 | 当前 mock 和 live 检索的知识来源 | 生产知识库、真实企业数据 |

### 2.2 已观察到的当前能力

以下内容在当前代码或已有项目文档中存在，但“代码存在”不等于“所有路径已经由作者本人验证”：

- Python FastAPI 提供 /health 和 /analyze。
- Python 支持 mock、live、auto 配置语义，并在分析结果中返回 mock、live 或 fallback。
- mock 模式使用本地规则分类和本地知识检索。
- live 模式包含 OpenAI Responses API 结构化输出和 Embedding 检索代码。
- Java 保存工单和分析运行记录。
- Java 记录分析来源工单版本，并对过期分析结果进行冲突保护。
- Java 对 AI 服务调用失败提供本地 fallback。
- 前端展示分类、置信度、分析轨迹、检索证据、引用、建议回复、人工升级原因和分析模式。
- 当前知识数据是本地 JSON 文件，当前向量存储是进程内存实现。
- Java Security 当前为演示用开放配置，尚未提供真实身份认证和 RBAC。
- H2 当前为内存数据库，应用重启后数据会重新初始化。

## 3. 目标版本定义

### 3.1 V1 当前版本

V1 的定位是本地可运行的端到端演示原型。

V1 必须满足：

- 三个服务可以分别启动。
- mock 模式不依赖外部 API。
- 浏览器可以完成工单查看和分析演示。
- 分析结果明确标识运行模式。
- 知识片段可以追溯到来源。
- 无证据时不会生成无依据的确定性承诺。
- AI 服务不可用时，系统保留人工处理路径。
- Java、Python、前端各自的基础检查能够重复通过。

V1 不承诺：

- 真实企业客户数据。
- 真实身份认证。
- 多租户隔离。
- 生产级数据持久化。
- 真实模型效果指标。
- 高并发或长时间稳定性。
- 自动执行退款、封号、数据删除等高风险动作。

### 3.2 V1.5 目标版本

V1.5 是本路线的主要目标。它不追求企业基础设施齐全，而追求“工程能力可证明”。

V1.5 完成后应具备：

- 固定的离线评估集。
- 可重复的 mock 评估脚本。
- 统一的 Java-Python-React 响应契约。
- 清晰的错误分类和 fallback 语义。
- 可追溯的 traceId、analysis run、工单版本和运行模式。
- 人工审核入口和分析结果来源说明。
- 真实 live 模式的可选验证路径。
- 结果、指标和 README 不互相矛盾。
- 一份 5 至 8 分钟可复现演示脚本。

### 3.3 V2 只作为演进方向

以下能力不属于当前主线，除非岗位目标明确要求，否则不进入本轮：

- MySQL 生产迁移。
- Redis 缓存、限流和分布式幂等。
- pgvector、Milvus 或 Elasticsearch。
- 消息队列和异步任务平台。
- JWT/OAuth2、RBAC 和多租户。
- Docker Compose、CI/CD 和云部署。
- OpenTelemetry、Prometheus、Grafana。
- 多模型路由。
- 多智能体自主执行。
- 自动退款、封号或修改客户数据。
- 模型微调。

## 5. P0：基线冻结与可复现运行

### P0-01 记录工作区基线

目标：明确后续所有变化基于什么状态。

执行内容：

1. 记录当前日期、分支和 git status --short。
2. 记录 Java、Python、Node.js 和 npm 版本。
3. 记录三个服务的依赖安装状态。
4. 记录当前测试、lint 和 build 命令。
5. 记录当前 README.md 与代码是否一致。
6. 标记当前未提交改动，不把它们误认为已经发布的版本。

建议记录文件：

~~~text
docs/verification/baseline-2026-08-11.md
~~~

这个文件可以记录命令和结果，但不能把“本次工具运行通过”改写成“作者亲自完成了全部测试”。

### P0-02 固定三种启动模式的边界

默认模式必须保持：

~~~text
AI_MODE=mock
~~~

三种模式的准确语义：

| 模式 | 外部 API | 结果来源 | 适用场景 |
| --- | --- | --- | --- |
| mock | 不调用 | 本地规则和本地知识 | 默认开发、面试预检、离线测试 |
| live | 调用 | OpenAI 结构化输出和 Embedding | 有 API Key 时单独验证 |
| fallback | 可能调用失败或证据不足 | 本地降级结果和人工审核路径 | 保护业务连续性 |

验收标准：

- 前端能显示实际模式。
- Java fallback 不被页面误显示为 live 成功。
- Python 健康检查能显示 mode 和 liveReady。
- README 不把 mock 检索写成真实语义 RAG。

### P0-03 固定最小手动演示

演示只保留两条主路径：

路径 A：有证据的正常分析

~~~text
打开工单
  -> 点击分析
  -> 查看分类和优先级
  -> 查看知识片段和来源
  -> 查看带引用的回复建议
  -> 人工审核或编辑
~~~

路径 B：无证据的安全降级

~~~text
打开知识库没有覆盖的问题
  -> 点击分析
  -> 显示没有充分证据
  -> 进入 fallback 或人工审核
  -> 回复不承诺未验证的结果
~~~

验收标准：

- 每条路径可以在 2 分钟内完成。
- 页面不需要解释隐藏思维链。
- 页面能说明结果来自 mock、live 还是 fallback。
- 失败场景不是空白页，也不是假装成功。

### P0-04 P0 完成定义

P0 完成前不开始新增业务功能。

完成条件：

- 三个服务检查命令可复现。
- Python 直接和间接依赖可按带 hash 的锁文件复现。
- mock 主流程和无证据流程可复现。
- 工作区变更边界已记录。
- README 的启动命令、服务端口和环境变量与实际代码一致。
- 已知限制清单已写入项目文档。

## 6. P1：契约与业务一致性

P1 的目标不是增加 AI 功能，而是避免同一个结果在三层被理解成不同的结果。

### P1-01 建立跨服务契约表

建议新增：

~~~text
docs/contracts/analysis-contract.md
~~~

契约表至少记录以下字段：

| 字段 | Java | Python | React | 规则 |
| --- | --- | --- | --- | --- |
| id | 分析运行 ID | 生成分析 ID | 展示历史和最新结果 | 每次分析唯一 |
| traceId | 请求链路 ID | 原样保留 | 错误和结果均可展示 | fallback 不重新生成 |
| status | 持久化状态 | 返回分析状态 | 显示流程状态 | 枚举固定 |
| mode | 保留实际模式 | mock/live/fallback | 显示标签 | 不允许隐式转换 |
| modelName | 保存结果字段 | 返回实际或占位模型名 | 展示来源 | mock 不伪装为真实模型 |
| promptVersion | 保存 | 返回 | 展示或诊断 | 每次策略变化更新 |
| classification | 业务结果 | 结构化输出 | 分类面板 | 字段和枚举统一 |
| retrieval.hits | 保存 JSON | 生成 | 证据面板 | 来源、排名、分数可追溯 |
| suggestedReply | 保存 JSON | 生成 | 编辑和审核 | 引用和警告不能丢失 |
| decision | 保存 JSON | 生成 | 升级提示 | 高风险规则统一 |
| usage | 保存或展示 | 生成 | 可选展示 | token 为 live 数据，mock 为 0 |

验收标准：

- 任何字段改动都能定位到三层影响。
- 状态、优先级、情绪和模式不再使用自由字符串。
- 前端不再只依赖 TypeScript 编译期断言来相信网络响应。
- 错误响应也有可解析的结构。

### P1-02 统一错误矩阵

建议新增：

~~~text
docs/contracts/error-contract.md
~~~

至少覆盖：

| 场景 | Python 行为 | Java 行为 | HTTP 语义 | React 行为 |
| --- | --- | --- | --- | --- |
| 工单不存在 | 不参与 | 返回业务错误 | 404 | 显示工单不存在 |
| 请求字段非法 | FastAPI 校验失败 | 不转成成功结果 | 400/422 | 显示字段错误 |
| 知识证据为空 | 返回 fallback 语义 | 保存可审核降级结果 | 200 + FALLBACK 或明确业务状态 | 显示证据不足 |
| AI 外部调用超时 | 抛可恢复错误 | 进入 fallback | 200 + FALLBACK 或明确错误码 | 显示降级原因 |
| 模型结构化输出非法 | 不静默吞掉 | 进入明确降级或失败 | 错误码可区分 | 显示需要人工审核 |
| 工单版本变化 | 不覆盖 Java 数据 | 返回冲突 | 409 | 刷新工单并提示旧结果无效 |
| Java API 不可用 | 无法请求 | 不适用 | 网络错误 | 进入明确的演示或不可用状态 |
| Python API 不可用 | 不适用 | 记录并 fallback | 由 Java 返回稳定结果 | 显示 AI 服务不可用 |
| 未知程序缺陷 | 保留真实错误 | 不伪装成普通 fallback | 5xx | 显示错误并保留 traceId |

关键原则：

- fallback 只处理可命名的外部依赖或证据不足问题。
- 程序错误不能全部被吞掉并改写为“AI 不可用”。
- 前端不能只看 HTTP 状态码而丢掉 code、message、traceId 和 details。
- 同一条请求的 traceId 在 Java fallback 后仍然保持一致。

### P1-03 完善版本和幂等边界

当前已经有部分工单版本冲突保护。后续应完成：

1. 分析开始时读取 sourceTicketVersion。
2. 分析结束时只允许将结果写入相同版本的工单。
3. 版本不一致时保存冲突信息，不覆盖当前工单。
4. 对重复点击分析增加幂等策略。
5. 对前端网络重试和用户重复点击进行区分。
6. 分析历史中保存分析来源版本、运行模式和 traceId。
7. 前端在分析进行中禁用同一工单的重复触发，但不能用单一全局状态阻塞其他工单。

推荐的幂等键语义：

~~~text
ticketId + sourceTicketVersion + analysisPolicyVersion
~~~

若后续加入客户端请求 ID，则使用：

~~~text
ticketId + sourceTicketVersion + requestId
~~~

验收标准：

- 同一版本重复请求不会产生无法解释的重复结果。
- 旧分析不能覆盖新版本工单。
- 冲突返回稳定的 409 结构。
- 分析历史能够解释每条结果基于哪个工单版本和策略版本。

### P1-04 处理演示数据和真实数据的边界

当前前端支持后端不可用时的演示数据模式。后续必须明确：

- 演示数据模式只允许用于页面预览和本地 UI 开发。
- 演示数据不能显示成已完成的真实分析。
- Java API 已启动但 Python 不可用时，不能把 Python AI 结果伪造为真实成功。
- 生产配置不能保留开放的 permitAll、H2 Console 和自动演示数据初始化。
- README 必须把“后端不可用时的前端演示”与“完整端到端运行”分开说明。

### P1-05 P1 完成定义

P1 完成条件：

- 契约表和错误矩阵已与代码一致。
- Java、Python、React 对分析结果字段和错误字段的解释一致。
- 版本冲突、重复分析和 fallback 语义有测试保护。
- 所有请求都能通过 traceId 关联到一次分析运行。
- 演示数据不会伪装成 live AI 结果。

~~~json
  "id": "billing-001",

  "description": "账单中有两笔相同金额，请尽快核对。",
  "current_category": "BILLING",
  "expected_category": "BILLING",
  "expected_priority": "HIGH",
  "expected_escalation": true,
  "expected_evidence_ids": ["kb-billing-duplicate-charge"],
  "evidence_required": true,
  "reply_constraints": [
    "must_cite_evidence",
    "must_not_promise_refund"
  ]
}
~~~

评估集不应保存真实客户个人信息。所有工单都使用模拟或脱敏内容。

### P2-02 样例覆盖矩阵

第一版建议 15 至 20 条，不追求数量，追求边界覆盖：

| 类别 | 至少覆盖 |
| --- | --- |
| BILLING | 重复扣款、账单核对、退款结果不能直接承诺 |
| ACCOUNT_ACCESS | 企业登录失败、SSO、账号锁定 |
| DATA_EXPORT | 导出处理中、任务编号、超时 |
| PRIVACY | 数据删除、隐私请求、授权材料 |
| TECHNICAL | 错误码、客户端版本、环境信息 |
| SUBSCRIPTION | 套餐、成员上限、席位费用 |
| DATA_RECOVERY | 知识库无覆盖、历史数据恢复 |
| GENERAL | 没有明确分类关键词 |
| 输入边界 | 空描述、长文本、大小写差异、中英文混合 |
| 安全边界 | 工单正文包含“忽略系统规则”等提示注入文本 |

每个类别至少有一个正常样例和一个边界样例。无证据样例必须单独统计，不能和正常命中样例混在一起。

### P2-03 评估脚本职责

评估脚本只调用本地 mock 工作流或本地 /analyze，不调用外部模型。

脚本应：

1. 加载 JSONL 样例。
2. 调用分析接口。
3. 保存每条输入、输出和错误。
4. 计算结构化指标。
5. 输出 Markdown 或 JSON 报告。
6. 记录运行时间、代码版本和知识数据版本。
7. 失败时返回非零退出码，阻止把坏结果当成通过。

不应做：

- 不比较完整自然语言回复是否逐字相同。
- 不把 Prompt 文本快照当成模型质量测试。
- 不从输出结果本身反推期望值。
- 不把一轮运行结果写成长期真实准确率。
- 不使用未经人工检查的随机工单作为唯一评估集。

### P2-04 第一版指标

#### 分类准确率

~~~text
分类准确率 = 分类正确样例数 / 有明确期望分类的样例数
~~~

#### 高风险升级召回率

~~~text
升级召回率 = 正确进入人工升级的高风险样例数 / 高风险样例总数
~~~

高风险漏升级比普通分类错误更严重，应单独看待。

#### 检索 Hit@K

~~~text
Hit@K = Top K 中包含至少一个期望知识片段的样例数 / 需要知识证据的样例数
~~~

#### 引用覆盖率

~~~text
引用覆盖率 = 回复引用了实际采用知识片段的样例数 / 有知识证据的样例数
~~~

#### 无证据安全率

~~~text
无证据安全率 = 正确进入 fallback 且没有作出无依据承诺的样例数 / 无证据样例数
~~~

#### 延迟

至少记录：

- 平均耗时。
- p50。
- p95。
- 最大耗时。

mock 延迟只能用于本地回归，不得直接类比 live 延迟或生产性能。

### P2-05 评估结果文件

建议输出到：

~~~text
services/support-copilot-ai/evaluation/reports/
  mock-YYYY-MM-DD.json
  mock-YYYY-MM-DD.md
~~~

报告至少包含：

- 运行时间。
- Git commit 或工作区状态。
- Python、Java、Node 版本。
- 知识数据版本。
- 样例数量。
- 每项指标。
- 失败样例 ID。
- 失败原因。
- 是否阻断发布。
- 与上一基线的差异。

评估报告不应直接覆盖旧报告。每次运行生成独立文件，便于比较。

### P2-06 评估验收标准

第一版固定评估集验收：

- 所有样例都有明确的期望分类或明确标记为开放分类。
- 所有需要证据的样例都有期望知识片段 ID。
- 无证据样例能稳定进入 fallback。
- 高风险样例不会静默变成普通成功。
- 回复不包含测试集要求禁止的确定性承诺。
- 评估脚本可重复运行。
- 失败样例能定位到分类、检索、生成约束或降级逻辑中的一层。
- README 只引用实际生成的评估报告，不手写评估数字。

## 8. P3：RAG 检索质量

当前项目的 mock 检索适合演示和回归；live 模式包含向量检索代码。P3 的目标是把两者的语义边界写清楚并可比较。

### P3-01 明确检索层次

推荐检索链路：

~~~text
工单输入
  -> 查询构建
  -> 候选召回
  -> 元数据过滤
  -> 排序或重排
  -> Top K 证据
  -> 证据约束回复
~~~

每层必须有单一职责：

- 查询构建：从工单内容生成查询，不改变工单事实。
- 候选召回：尽量减少漏召回。
- 元数据过滤：按类别、文档状态和权限过滤。
- 排序或重排：提高相关内容排序。
- Top K：限制传给模型的上下文大小。
- 证据约束：让回复引用已采用的片段。

### P3-02 统一 Top N、Top K 和阈值

当前需要确认并固定：

- topN 是候选召回数量。
- topK 是最终证据数量。
- topK <= topN。
- mock 模式和 live 模式对参数含义一致。
- enableRerank 若未实现，不能在界面显示为已启用。
- 检索阈值必须由配置或明确常量控制。
- 没有超过阈值的结果时返回空证据，而不是返回低质量片段充数。

验收标准：

- 修改 topK 会真实改变返回证据数量。
- 修改阈值会真实改变空证据和命中结果。
- mock 与 live 的响应字段一致。
- 检索方法、初始排名、最终排名和分数含义写入契约文档。

### P3-03 知识数据规范

每个知识片段至少包含：

- chunk_id。
- document_id。
- document_title。
- section。
- content。
- source_uri。
- categories。
- keywords。
- document_version。
- status。
- updated_at。

第一版继续使用本地 JSON 即可，不要因为“RAG”三个字就立即引入向量数据库。

知识数据必须满足：

- chunk_id 稳定。
- 同一文档的片段可以追溯。
- 已归档文档不参与默认检索。
- 分类标签与内容基本一致。
- 片段不要包含系统指令式文本。
- 片段中的客户输入或外部文本必须被视为数据，不是 Prompt 指令。

### P3-04 检索对比实验

在固定评估集上分别运行：

1. 当前本地规则检索。
2. live Embedding 检索，条件允许时。
3. 混合检索或重排策略，只有代码真实实现后再加入。

每种策略都记录：

- Hit@1、Hit@3。
- 空证据误判率。
- 高风险知识片段漏召回数。
- 平均和 p95 检索耗时。
- 运行成本或 token 影响，若是 live 模式。

不要把某种策略的单次结果写成普遍结论。至少重复运行并记录运行环境。

### P3-05 证据约束回复

回复生成必须遵守：

- 有政策或流程结论时必须能对应知识片段。
- 无证据时降低置信度并进入人工审核。
- 不承诺退款、恢复、删除、到账时间等未经证实的结果。
- 回复引用只能引用本次实际采用的片段。
- 不展示隐藏思维链，只展示可审计的简短理由和证据。
- 知识片段中的提示注入文本不能改变系统规则。

### P3-06 P3 完成定义

P3 完成条件：

- 检索参数语义固定且可测试。
- 知识片段可追溯。
- mock 检索评估已经有稳定基线。
- live 检索若未验证，只保留为可选模式，不写成已达成效果。
- 无证据和提示注入样例有回归测试。
- 任何检索指标都有评估集、运行时间和策略版本。

## 9. P4：Live 模型与降级

P4 只有在拥有可用 API Key、模型配置、网络和调用预算时执行。没有这些条件时，P0-P3 仍然可以完成，不应为了简历临时付费或提交密钥。

### P4-01 Live 前置条件

执行前需要明确：

- API Key 来源和账户权限。
- 聊天模型名称。
- Embedding 模型名称。
- API Base URL。
- 单次调用预算。
- 网络可达性。
- 测试数据是否脱敏。
- 是否允许把工单文本发送到外部服务。

密钥只允许通过环境变量或本地 .env 读取，不能写入源码、截图、测试样例或 Git 历史。

### P4-02 调整超时预算

当前 Java 和 Python 都有自己的超时与重试配置。后续必须保证：

~~~text
Java 总等待预算
  > Python 单次处理预算
  > Python 外部调用超时 × 重试次数 + 连接和序列化余量
~~~

实际配置不应让 Java 先超时并返回 fallback，而 Python 仍在后台继续消耗模型调用预算。

验收标准：

- 超时配置在 README 和环境变量模板中一致。
- 运行日志能区分连接超时、模型超时、Embedding 超时和结构化响应失败。
- 重试次数有限。
- 重试不会造成业务数据重复写入。
- 失败后 fallback 结果明确标记为 fallback。

### P4-03 结构化输出验证

live 模型只允许返回符合 ModelDraft 或等价契约的结构化结果：

- 分类是允许的枚举或受控字符串。
- 优先级是允许的枚举。
- 情绪是允许的枚举。
- 置信度在 0 到 1。
- 理由长度受限。
- 回复正文存在。
- warnings 是结构化列表。
- 未知字段被拒绝或明确处理。

模型输出不符合结构时：

1. 记录结构化错误。
2. 不把非法内容直接写入业务数据。
3. 进入可解释的 fallback 或人工审核。
4. 保存 traceId 和 analysis run。
5. 在评估报告中统计。

### P4-04 外部数据边界

live 模式上线前至少设计：

- 邮箱、电话、身份证号、支付信息等敏感内容的识别。
- 发送模型前的脱敏策略。
- 脱敏后的内容是否仍可支持分类和检索。
- 原文是否禁止写入日志。
- 模型供应商、Base URL 和数据处理范围记录。
- 用户是否需要知道结果经过外部模型处理。

当前没有完成脱敏和合规设计前，不把 live 模式描述为可处理真实企业工单。

### P4-05 Live 验收

至少完成以下测试：

| 测试 | 通过条件 |
| --- | --- |
| 正常 live 分类 | 返回结构化结果，mode 为 live |
| 有证据 live 回复 | 引用本次采用的知识片段 |
| 无证据 | 降低置信度并要求人工审核 |
| Embedding 失败 | 进入可解释降级 |
| 结构化输出异常 | 不写入非法结果 |
| API 超时 | 在预算内结束并返回 fallback |
| API Key 缺失 | 启动或请求阶段明确报错，不发送空凭证 |
| 提示注入 | 工单或知识片段不能覆盖系统规则 |
| 重复请求 | 不产生无法解释的重复分析记录 |

没有完成这些测试前，简历只写 mock 链路和 live 接口预留。

## 10. P5：人工审核、安全与审计

### P5-01 把 AI 结果定义为建议

业务原则：

- 工单、客户信息、状态和负责人是业务事实。
- 分类、优先级建议、知识依据和回复内容是 AI 建议。
- AI 不直接完成退款、封号、删除、恢复、改价或权限变更。
- 高风险分类必须进入人工审核。
- 人工可以编辑、拒绝、采纳或覆盖 AI 建议。
- 人工覆盖原因应可记录。

### P5-02 审核状态

建议区分：

~~~text
ANALYSIS_READY
READY_FOR_MANUAL_REVIEW
APPROVED
EDITED
REJECTED
STALE
FALLBACK
~~~

状态命名必须与现有前端、Java DTO 和数据库字段统一，不能在不同层使用多个近义词。

每个审核动作至少记录：

- 操作人或演示用户标识。
- 操作时间。
- 分析运行 ID。
- 原始建议。
- 修改后内容或修改摘要。
- 操作类型。
- 工单版本。
- traceId。

### P5-03 权限边界

当前 permitAll 只能作为本地演示配置。若进入真实数据或部署阶段，至少需要：

- 一线客服：查看和处理分配给自己的工单。
- 主管：审核高风险结果和查看指标。
- 知识库管理员：维护知识文档和索引。
- 审计人员：查看分析历史和操作记录。
- 系统管理员：管理配置和服务状态。

如果暂时不实现登录，应在 README 中明确写成“演示环境开放配置”，并把认证列为后续范围，不能声称已有权限系统。

### P5-04 生产配置隔离

必须隔离：

- H2 Console。
- 演示数据初始化器。
- permitAll。
- 前端本地演示数据。
- 外部模型 Key。
- 本地日志中的工单正文。
- 测试数据库和生产数据库。

验收标准：

- dev 配置可以方便演示。
- test 配置不会访问外部 API。
- prod 配置不会自动插入演示数据。
- 生产配置不暴露 H2 Console。
- 日志不打印完整敏感工单正文。

### P5-05 P5 完成定义

P5 完成条件：

- AI 只能产生建议，不执行高风险业务动作。
- 审核结果与原始分析结果可区分。
- 高风险结果有人工审核路径。
- 演示开放配置与真实权限边界在文档中明确区分。
- 敏感数据发送和日志策略已经明确。

#### 业务指标

- 未解决工单数。
- 高优先级工单数。
- SLA 风险工单数。

- 引用覆盖率。
- 无证据安全率。

页面展示的 AI 指标必须来自评估报告或持久化评估运行，不能继续使用没有来源的静态数字。

### P6-03 前端 AI 状态

前端至少要明确展示：

- 分析中。
- 分析成功。
- mock 结果。
- live 结果。
- fallback 结果。
- 无证据。
- 需要人工审核。
- 工单版本冲突。
- Java API 不可用。
- Python AI 服务不可用。
- 当前数据是演示数据。

前端不应：

- 展示不存在的实时进度。
- 把静态数字标成实时指标。
- 把 mock 结果的模型名称显示成真实模型。
- 在请求失败后保留看起来像成功的新数据。
- 让一个工单的分析状态阻塞其他工单。

### P6-04 拆分大型前端文件

App.tsx 已经承担较多布局、状态和业务交互。拆分应在功能稳定和测试保护后进行：

建议方向：

~~~text
apps/support-copilot-web/src/
  features/tickets/
    TicketQueue.tsx
    TicketDetail.tsx
    ticketState.ts
  features/analysis/
    AnalysisPanel.tsx
    EvidencePanel.tsx

  features/dashboard/
~~~

拆分原则：

- 先锁定行为测试，再移动代码。

- 请求、错误解析和响应校验集中在服务边界。
- 不为了拆文件引入新的状态管理库。
- 不在拆分过程中同时新增 AI 功能。

### P6-05 性能提示处理顺序

当前构建存在 bundle 体积提示。处理优先级：

1. 先确认功能和评估链路稳定。
2. 再检查 ECharts 是否可按页面或功能懒加载。
3. 再考虑路由级代码分割。
4. 最后比较构建体积变化。

当前不建议为了消除提示而大规模替换 UI 库或重写页面。

### P7-02 演示脚本


5 至 8 分钟演示顺序：
