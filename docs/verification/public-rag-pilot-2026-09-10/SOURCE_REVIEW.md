## 结论与范围

建议用 GitHub CLI 的公开实际问题作为试标注输入，以同一产品的官方手册和固定提交中的帮助文本作为证据。可验证的能力限定为“公开开发工具支持问题上的证据检索与回复”，不能外推为真实企业客服生产效果。GitHub CLI 官方仓库说明其由 GitHub 团队维护，问题可以提交到该仓库；这支持选择该产品的来源一致性，但不能证明任意 issue 内容或维护者回复正确。[官方项目说明](https://github.com/cli/cli/blob/trunk/docs/gh-vs-hub.md)

当前可复核的上游 trunk 提交为 `093c348510736308b88e6ca3dd0adc801e291a8b`，提交时间 `2026-09-09T18:28:06Z`，由只读 GitHub API 查询获得。它只用于核查来源和文档生成方式。**本轮实际 corpus 选择已安装的 GitHub CLI 2.100.0（2026-09-03）输出的官方帮助文本**，由主任务记录二进制 SHA、`v2.100.0` 提交元数据及 MIT 许可证；不得把上述 trunk SHA 写成实际 corpus 版本。每道题仍需确认其产品版本与该帮助文本是否适用。

## 许可证与问题文本的区别

`cli/cli` 的 MIT 许可证明确覆盖软件与相关文档，并要求在副本或实质性部分中保留版权及许可说明。适用该许可证的 corpus 应保留许可证和来源，不只保留清洗后的正文。[固定提交 LICENSE](https://github.com/cli/cli/blob/093c348510736308b88e6ca3dd0adc801e291a8b/LICENSE)

GitHub 服务条款 D.3 说明用户内容的所有权；D.5 涉及公开内容查看与平台内复制；D.6 说明向带许可证仓库贡献内容的条款。这些条款不能替代逐项确认 issue 内第三方日志、截图、引用或附件的权利。本轮不把整个 issue 讨论统一标记为 MIT，也不发布全文数据集。[GitHub 服务条款 D 节](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service#d-user-generated-content)

本试标注的选择是保存 issue URL、编号、时间、版本线索、原始 body 的 SHA 及简短来源归纳，避免复制完整讨论。逐条标题仅保留短标题（不超过 25 个词），问题输入明确标记 `PUBLIC_ISSUE_ADAPTED`，审核状态为 `NOT_REVIEWED`；归纳不是原始用户逐字输入，原文哈希也不代表已审核。许可未确定的正文不进入可分发数据包。这是本项目的保守资料管理决定，不是对一切公开 issue 再利用作统一法律结论。token、邮箱、主机名等即便公开出现，也不需要为评测收集或保留。

## 时间、答案泄漏与分布限制

以下是本轮建议的评测约束，尚未全部执行：

1. **先选定时间语义。** 使用当前文档回答旧问题只能叫“当前文档下的公开问题回放”。如果声称重现问题发生当时的客服能力，必须使用当时已存在的文档，并核对 CLI、操作系统、GitHub 服务版本。不能拿事后修复说明冒充当时可得证据。
2. **输入只含首轮问题和必要已知上下文。** 后续评论、解决方案、关闭原因和修复 PR 可用于审题，但不能加入模型输入或检索 corpus。关闭不等于解决，标签不等于标准答案。
3. **来源真实不等于模型未见。** 公开 GitHub 问题可能出现在模型训练中，当前没有训练数据审计能力。因此结果不能宣称排除预训练污染。保留无检索对照，观察检索带来的增量。
4. **开发与测试按问题簇隔离。** 重复 issue、同一故障的改写、相同修复关联的案例应在同一集合；已用于提示词或规则修复的案例不再作为独立未见测试。
5. **不要只选择能答的问题。** 候选中应保留缺少版本、文档不覆盖、已知故障、需要现场诊断等情况；人工分别标为可答、需补问或证据不足。未知原因应保持未知。
6. **查询策略影响分布。** 如果用 auth、token 等词搜索，结果只能代表该专题的目的性抽样。候选数量、人工审核数量与最终冻结测试数量分别报告，不能把数个专题案例写成随机业务样本。
7. **不要只放正确文档。** corpus 中同时保留同产品相邻命令、相近概念和无关文档作为真实干扰；精确标注证据段落和版本，再映射到不同实验的 chunk。

## 最小试标注验收

本轮资料整理的正常路径是：公开原始问题 → 保留症状与上下文的归纳 → 定位官方证据 → 写出待人工审核的要点与禁止推断。一个合格候选需能回到原问题和官方证据，且清楚区分“观察到的症状”与“推断出的原因”。

相关失败路径是：文档只说明如何配置，却无法证明问题根因；此时标记为需补问或证据不足，不补写唯一答案。另一失败路径是版本冲突或来源不足；将案例隔离为待确认，不静默删除以提高通过率。

开始模型评测前至少需要：确认每题输入、时间/版本范围、可答性、证据段落、关键处理要点与禁止承诺；记录人工审核者及分歧处理；冻结问题和 corpus 哈希。模型辅助整理不计入人工审核数量。第一批只做开发/试标注用途，不能当作已冻结、无泄漏的正式测试集。

主任务本轮采用 `how in:title` 的已关闭问题作目的性抽样，计划从 48 条候选中整理 20 条，保留难题与范围外问题。全部归入 pilot-development，不做测试拆分，不填造可答标签或质量分数。最终入选数量和逐条来源由候选清单记录；这组问题不能代表随机客服请求分布。
