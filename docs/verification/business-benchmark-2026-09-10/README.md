# 工单业务链路与公开参考评测

2026-09-10 已完成 96 次真实工单分析：32 个固定输入分别运行于 1、2、4 并发。全部结果经 Java 保存、即时读回及 Java 重启后读回匹配。共 64 次正常 live 分析、14 次证据不足降级、18 次模型读取超时。**业务链路可以保留失败结果，但正常模型产出和检索质量仍有缺口。**

完整结果见 [逐题对照](RESULTS.md)、[汇总 JSON](summary.json)、[逐题指标](scored-trials.json)、[重启验证](restart-verification.json)。这轮是固定条件的本地基准，不是生产容量或客户问题解决率验收。

## 数据来源及评测口径

使用 [Doc2Dial 官方数据仓库](https://github.com/doc2dial/doc2dial.github.io) 的 `doc2dial_v1.0.1.zip`。数据是基于公开文档由人类编写的服务对话，包含发布者提供的回复和文档跨度标注；不是本项目模型生成的标准答案，也不是企业真实客服日志。官方方法见 [Feng 等，EMNLP 2020](https://aclanthology.org/2020.emnlp-main.652/) 和 [数据说明](https://doc2dial.github.io/README.html)。

- 原归档 SHA-256、下载源对应仓库 revision、原始 JSON SHA-256 和抽样规则冻结于 [protocol.json](protocol.json)。归档文件名为 v1.0.1，内部 README 标为 v1.0，实际使用归档内的 test 对话；以文件摘要为准，不将它冒充论文原版官方成绩。
- 对每段对话，仅选择首个 user/agent 对，要求 agent 的 act 为 respond_solution 且有 solution/precondition 参考。按固定盐的 SHA-256 排序，每域选择 8 个不同文档，得到 32 题；没有按运行结果筛选或替换样本。
- 全部 488 份文档进入知识库，不仅包含选中问题的正确文档。按 2000 个 Unicode code points、1600 步长切为 1564 块，保持原始跨度映射，不按照答案位置切块。
- 参考答案与标注仅进入离线评分器；模型输入是 user 原话、归档评测说明和实际检索内容。工单标题来自问题，不含标注文档名或答案。类别、客户身份是统一的实验元数据，不冒充真实客户。
- 基准知识库单独导入全套生产 Python 检索/生成/回复处理与 Java API；默认工作台的 SaaS 知识库与此前 22 例回归报告保持原状态。此实验衡量公开服务领域的项目运行表现，不能直接证明默认 SaaS 业务政策效果。
- 质量主组是并发 1 的 32 题；并发 2/4 是同题重复观察，不是额外 64 个独立质量样本。组顺序固定，不能据此断言并发导致某次外部网关超时。

## 实测环境与链路

Apple M1，8 个逻辑 CPU，8 GiB 内存，macOS，Java demo profile、独立文件 H2（MySQL 兼容模式、Flyway）和本地 Python 服务。原开发工作台同时存在，硬件不是独占压测环境。模型配置名为 gpt-5.6-luna，Embedding 为 Qwen/Qwen3-Embedding-0.6B（1024 维）；模型身份仅由配置与调用记录佐证，不能独立证明网关内部路由。[配置记录](provider-config.json)、[运行清单](run-1/manifest.json)。

```text
创建工单 HTTP
→ Java 保存工单
→ 分析 HTTP
→ Java 读取工单与知识发布
→ Python 真实向量检索、模型生成、回复与降级处理
→ Java 保存分析和业务事件
→ 分析 HTTP 返回
→ GET 分析历史并逐项比对
→ 服务停止，Java 使用同一文件 H2 重启，再次 GET 比对
```

计时从创建请求前开始，至分析响应接收完成；Java 在返回分析前已经落库。该区间包含创建、HTTP、检索、模型、回复处理和保存，但不包含浏览器渲染、人工审核或最终业务解决。额外的 GET 耗时另存。p50/p95 使用 nearest-rank，包含降级与超时路径；第一张工单包含冷索引加载。页面中派生的工作流步骤时间不作为本轮性能计时依据。

SDK 不重试，实验 HTTP 客户端没有应用层重试；Java-to-Python 沿用最多 2 次服务请求的配置。模型读取超时转成 HTTP 200 的明确 FALLBACK，所以不能以 HTTP 200 数量替代正常 AI 分析数量。真实检索在生成前单独记录，即使后续本地 fallback 替换了返回证据，也不会混入真实检索指标；这一记录增加的少量本地文件写入开销计入本轮观察。

## 回答质量：独立参考对照

主组 32 题结果：

| 指标 | 结果 | 能证明什么 |
| --- | ---: | --- |
| 发布者标注文档命中 @3 | 19/32，59.38% | 前三条真实检索是否包含发布者标注的那份文档 |
| 标注证据字符覆盖均值 | 49.86% | 同文档检索区间覆盖了多少标注跨度；重叠合并 |
| 标注证据全覆盖题数 | 15/32，46.88% | 标注跨度是否全部进入检索上下文 |
| 引用了标注文档 | 17/32，53.13% | 最终引用是否落在发布者标注文档上，不证明全部结论有据 |
| 参考回复 token F1，全部题 | 11.94/100 | 与发布者回复的词语重叠；非 live 记为 0 |
| 参考回复 token F1，仅 live | 17.37/100 | 仅 22 份正常 live 回复的词语重叠，不隐去全量低分 |

发布者的跨度标签本身是 fuzzy annotation，且本次抽样包含 “Hi there” 等寒暄，以及缺少机构/业务上下文的首轮问题。例如一个寒暄关联了“补办证件无需视力检查”的参考跨度；另一题仅问忘记改地址，没有明确机构。真实回复可能合理补问、引用其他相关文档或比参考更长。因此 **59.38% 是指定标注文档命中率，11.94 是词语 F1，均不能称为业务回答准确率。**

保留这些记录是为了让数据缺陷也可审计；没有看到结果后删题提高分数。后续应先按预先写明的业务意图和上下文完整性标准，抽取未用于本轮的对话并核对参考，再冻结质量验收集。既有 20 条真实 GitHub Issues 归纳题仍是独立材料，见 [此前实验](../public-rag-experiment-2026-09-10/README.md)，不与本轮人工构建对话混成一种数据。

汇总提供 Wilson 95% 二项区间用于显示小样本不确定性；它不是对真实业务流量分布的保证。模型输出人工审核仍为 0，事实正确率、问题解决率、人工采纳率和节省工时均未测得。不能以自动 F1 或模型自评分填充这些数字。

## 处理耗时与稳定性

| 并发工单 | 正常 live | 无证据降级 | 模型读取超时 | 创建至分析保存 p50 | p95 | 正常 live 产出/分钟 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 22/32（68.75%） | 4 | 6 | 10.78s | 20.86s | 3.28 |
| 2 | 26/32（81.25%） | 6 | 0 | 9.39s | 18.39s | 8.94 |
| 4 | 16/32（50.00%） | 4 | 12 | 16.94s | 20.93s | 7.33 |

96/96 API 分析返回，96/96 即时读回匹配，96/96 在 Java 停止后使用原 H2 文件重启仍读回匹配。这证明本批次的事务保存与进程重启持久化，没有证明断电恢复、MySQL 生产性能、高可用或长期可靠性。

4 并发组包含降级的完成吞吐为 14.65 次/分钟，正常 live 产出却只有 7.33 次/分钟，低于该轮 2 并发的 8.94。不能只展示总吞吐。18 次模型故障均为 APITimeoutError / ReadTimeout；需要供应端日志才能确定网关、网络或模型端根因，不能仅凭本地观察宣布已定位服务端缺陷。

本轮测到的瓶颈范围：真实检索中位耗时约 0.13–0.19 秒，生成和其超时占据主要等待时间。该结果仍受当前文档量、远端服务时段与开发机负载限制；不是最大 QPS 或生产 SLA。

已报告 token 用量为部分可用数据；18 次超时及 Embedding 没有完整 usage，费用缺少实际网关单价，因此总费用保持未知。所有超时原始日志保留，不重试择优。

## 验证、故障与源码边界

基础 HEAD `4df3bf44907c34318132496929bad4a3974ad88b`，master，dirty，无提交/推送/部署。运行使用的 157 个源码/资源文件和 Java JAR 摘要绑定于 [source-manifest.json](run-1/source-manifest.json) 与 [manifest](run-1/manifest.json)。归档内保留运行时版本；后续只修正实验代码的类型注解和 unused-return 处理，没有更改该轮真实请求或结果。

- 数据抽样、全文分块、人工跨度回指和 corpus checksum 均已核对。指标测试 4 项覆盖重复词、重叠跨度、失败耗时进入 p95、小样本区间；索引批处理与既有检索观察测试合计 3 项通过。Python 新模块类型检查零错误/零警告，Ruff 使用仓库现有规则通过。
- 初次索引预检因未显式指定维度而失败，发生在调用 provider 之前；记录保留于 index-preflight-failure.log。明确配置 1024 维后，1564 行真实索引构建耗时 19.11 秒。没有把预检失败删去。
- 正常路径以完整 HTTP、live 输出、数据库读回和重启读回验证。失败路径以实际 18 次生成读取超时和 14 次业务证据不足验证；它们均保持明确 fallback，不记正常 live 成功。
- 来源下载曾尝试 TechQA，但本机无法完成官方站访问；没有把未取得的数据写成已使用。当前来源是可核验的 Doc2Dial 官方归档。
- 汇总核对全部 96 个 case/concurrency 配对、原始数据/源码哈希和真实 VECTOR 观察，见 [verification.json](verification.json)。没有运行全仓测试或宣称全仓发布通过。

新增代码分别负责数据准备、隔离运行、指标计算、报告生成、重启核对；Python 只增加分批索引适配和实验观察入口，生产业务代码未改。模块均低于 250 个非空/非注释行，没有新加类型忽略或广泛吞错来改变 AI 故障结果。

## 重建与复跑

从仓库根目录执行 `node scripts/benchmark/summarize-business.mjs` 可以不调用模型重建报告。原始下载位于 `.local/business-benchmark-source/`，实验数据库、日志和索引位于 `.local/business-benchmark-runtime/`，旧工作台没有重启或切换知识库。

原始运行命令及结果在 verification.json 中。`prepare-doc2dial.mjs` 与 `run-business.mjs` 会拒绝覆盖现有冻结材料/run-1；**这轮记录不要原地重跑**。下一轮需创建新的独立输出目录、更新明确的实验编号并保留旧快照；本轮脚本目前不是可随意覆盖的生产压测工具。

可用于简历的事实：在 488 份公开文档、1564 个真实向量分块上构建独立参考评测，完成 96 次跨 Java/Python 的 live 工单分析，对 1/2/4 并发下的耗时、降级、检索命中与结果持久化进行对照，验证 96/96 分析结果在服务重启后仍可读回。不能写未经测量的回答准确率、客服问题解决率、降本比例或生产并发容量。
